# Agent Guide: check_xxx_health Nagios Plugin Family

> **Why this file lives here, under this name:** it is maintained once, inside the
> shared `GLPlugin` framework repo, and reaches every `check_xxx_health` plugin as a
> `git submodule` — no per-repo copy to keep in sync. Each plugin repo exposes it at
> its own root as `./CLAUDE.md` and `./AGENTS.md`, both symlinks pointing here
> (`GLPlugin/.agents/AGENTSMD-FOR-PLUGINS.md`). The deliberately non-standard filename
> is intentional: it must **not** be named `CLAUDE.md`/`AGENTS.md` *inside GLPlugin
> itself*, or it would get auto-loaded as project instructions when someone is working
> directly on GLPlugin (a different project, with a different structure — a Perl
> distribution, not an autotools-based Nagios plugin) rather than on a plugin built on
> top of it. If you're reading this while working inside the `GLPlugin` repo itself
> rather than inside a `check_xxx_health` plugin repo, none of the project-structure
> guidance below applies to what you're doing — see GLPlugin's own README instead.

This file is identical across all `check_xxx_health` repositories (`check_nwc_health`,
`check_sap_health`, `check_ups_health`, `check_wut_health`, and any future sibling). It
documents the shared architecture so an agent can implement a new vendor/model without
first reverse-engineering the framework from scratch. Everything here was verified
against the actual code, not against project folklore — if something here stops
matching what you read in the repo, trust the repo and fix this file.

`check_xxx_health` is a placeholder for whichever plugin you are in
(e.g. `check_nwc_health`); `CheckXxxHealth` is the matching Perl namespace
(e.g. `CheckNwcHealth`).

## What these plugins are

Each repo builds one Nagios/Icinga plugin: a single Perl script,
`plugins-scripts/check_xxx_health`, that is queried with a `--mode <name>` and emits a
standard OK/WARNING/CRITICAL/UNKNOWN line plus perfdata. Internally the plugin
auto-detects the make/model of the monitored device (mostly over SNMP, sometimes over a
vendor RFC/API, sometimes by inspecting the local host) and dispatches to the
vendor-specific check logic for the requested mode. Adding support for a new
vendor/model means adding a Perl class, not touching the entry point or the build
machinery.

All four repos share one framework, **GLPlugin**, checked in as a git submodule. It
supplies the plugin base class, CLI argument parsing, threshold/perfdata handling, and
(for SNMP plugins) the MIB/OID layer. Vendor logic lives in the individual repo; generic
plumbing lives in GLPlugin.

## Repository layout

```
check_xxx_health/
  configure.ac                  # name + version (source of truth for both)
  configure                     # generated by autoreconf — do not hand-edit
  Makefile.am / Makefile.in     # top-level autotools glue
  GLPlugin/                     # git submodule, shared framework (own repo)
  MIBS/                         # raw vendor MIB files (reference material, not code)
  ChangeLog                     # human-readable release history
  plugins-scripts/
    check_xxx_health.pl         # entry point: mode + CLI option registration
    check_xxx_health            # BUILD OUTPUT — generated, never edit directly
    Makefile.am                 # lists every .pm file that gets bundled (see below)
    CheckXxxHealth/             # your vendor/model code lives here
      Device.pm                 # classify(): detects vendor, reblesses into it
      Vendor.pm                 # e.g. Cisco.pm: detects model, reblesses further
      Vendor/Model.pm           # e.g. Cisco/IOS.pm: dispatches modes to components
      Vendor/Model/Component/XxxSubsystem.pm
```

`CheckXxxHealth/` mirrors the plugin's Perl namespace exactly (folder name = package
prefix, CamelCase). A new vendor almost always means new files under this tree, never
changes to `Device.pm`'s siblings in GLPlugin.

## Build system

```
git submodule update --init   # GLPlugin/ is often NOT checked out — check first
autoreconf                    # configure.ac -> configure (only after editing configure.ac)
./configure                   # Makefile.am -> Makefile (only after editing a Makefile.am)
make                           # stitches plugins-scripts/check_xxx_health together
```

Before doing anything else, check whether `GLPlugin/` is populated
(`ls GLPlugin/lib` — if empty, run `git submodule update --init` first). Several of
these repos are checked out with the submodule uninitialized by default.

**Rule of thumb for which step to re-run:**
- Added/removed a `.pm` file → edit `plugins-scripts/Makefile.am`, then
  `./configure && make clean && make` (no `autoreconf` needed — `./configure`
  regenerates `Makefile` from `Makefile.am`, but only `autoreconf` regenerates
  `configure` itself from `configure.ac`).
- Bumped the version → edit `configure.ac`, then `autoreconf && ./configure`.
- Only edited the *contents* of an existing `.pm` file → `make` is enough.

### How the final plugin file is assembled

`plugins-scripts/Makefile.am` declares two file lists:

- `GL_MODULES` — framework files pulled from `../GLPlugin/lib/...`. These are only
  bundled into the standalone script when standalone mode is enabled (the default);
  they exist so the plugin can run without `Monitoring::GLPlugin` installed system-wide.
- `EXTRA_MODULES` — the plugin's own vendor/model code under `CheckXxxHealth/`. These
  are **always** bundled. **Every new `.pm` file you add belongs here.**

The build rule concatenates: shebang → `GL_MODULES` (if standalone) → `EXTRA_MODULES` →
the entry point `.pl`. While concatenating, it strips out `1;` (the module's true-value
return) and everything from `__END__` onward (`__PACKAGE__` too, for `GL_MODULES`).
Practical consequence: **never put logic after `__END__` in a module that gets
bundled** — only POD/documentation belongs there, since it will silently vanish from
the built plugin. This is a common way for "it works when I `perl -I` the module
directly, but not in the built plugin" bugs to happen — if you see that mismatch, check
what's after `__END__` first.

Forgetting to add a new file to `EXTRA_MODULES` is the single most common build mistake:
the file exists, `perl -c` on it passes, but it's simply absent from the built script.

## Runtime architecture: classify → rebless → dispatch → check

This is the part that matters most for adding a new vendor. Read a real example before
writing new code — `CheckNwcHealth::Cisco` and `CheckNwcHealth::Cisco::IOS` in
`check_nwc_health` are a clean, representative case to model against.

1. **Entry point** (`plugins-scripts/check_xxx_health.pl`, `run_plugin()`) instantiates
   `CheckXxxHealth::Device` and registers every mode the plugin supports:
   ```perl
   $plugin->add_mode(
       internal => 'device::hardware::load',   # internal dispatch key, used in init()
       spec     => 'cpu-load',                  # what the user passes as --mode
       alias    => ['cpu-usage'],
       help     => 'Check the CPU load of the device',
   );
   ```
   A brand-new *kind* of check (not just a new vendor) needs an `add_mode()` entry here.
   CLI options specific to the plugin are registered the same way with `add_arg()`
   (see "Common CLI options" below for what already exists — don't reinvent a flag).

2. **`Device::classify()`** decides what the target device *is*. For SNMP plugins this
   means calling `check_snmp_and_model()` (fetches `sysDescr`/`sysObjectID` etc.), then
   matching on `$self->{productname}` (a regex against sysDescr-like text),
   `$self->implements_mib('SOME-MIB')` (true if the device answers on that MIB's OID
   subtree), or a raw `sysObjectID` prefix — and reblessing the object into the matching
   vendor class:
   ```perl
   } elsif ($self->{productname} =~ /Cisco/i) {
     $self->rebless('CheckNwcHealth::Cisco');
   } elsif ($self->implements_mib('SYNOPTICS-ROOT-MIB')) {
     $self->rebless('CheckNwcHealth::Nortel');
   ```
   `rebless()` (and the older but equivalent raw `bless $self, 'Some::Class'`) changes
   `ref($self)` in place — same object, same accumulated SNMP data, new class and thus
   new method resolution. `map_oid_to_class($oidPrefix, $class)` is an alternative used
   in some repos for pure sysObjectID-prefix matching.

3. **Vendor class `init()`** (e.g. `Cisco.pm`) may rebless again into a more specific
   model class (`Cisco::IOS`, `Cisco::NXOS`, `Cisco::WLC`, ...) using the same
   productname/implements_mib checks, now narrowed to that vendor.

4. **Model class `init()`** (e.g. `Cisco::IOS.pm`) is where mode dispatch happens —
   this is almost always the method you're editing or adding a sibling to:
   ```perl
   sub init {
     my ($self) = @_;
     if ($self->mode =~ /device::hardware::load/) {
       $self->analyze_and_check_cpu_subsystem("CheckNwcHealth::Cisco::IOS::Component::CpuSubsystem");
     } elsif ($self->mode =~ /device::hardware::memory/) {
       $self->analyze_and_check_mem_subsystem("CheckNwcHealth::Cisco::IOS::Component::MemSubsystem");
     } else {
       $self->no_such_mode();
     }
   }
   ```
   `$self->mode` is the `internal` string from the matching `add_mode()` call.
   `no_such_mode()` is the required fallback for every branch chain — a mode this class
   doesn't implement should fail loudly, not silently return OK.

### `analyze_and_check_<name>_subsystem` — read this before grepping for it

`analyze_and_check_widget_subsystem("Some::Component::Class")` is **not a real method
you will find defined anywhere** — it's synthesized by an `AUTOLOAD` in
`GLPlugin.pm` for *any* name matching `analyze_and_check_*_subsystem`. Calling it with a
class name argument does exactly this:
```perl
$self->{components}->{widget_subsystem} = Some::Component::Class->new();  # -> calls its init()
$self->{components}->{widget_subsystem}->check();
```
So inventing a new subsystem name (`analyze_and_check_fan_subsystem`,
`analyze_and_check_licensepool_subsystem`, anything) costs nothing — you don't need to
register it anywhere. The only two things you must write are the `<name>` (any word) and
the `Component` class it points at. Don't waste time searching the codebase for where
`analyze_and_check_cpu_subsystem` is "defined" — it isn't, by design.

### Writing a Component class

A Component subsystem class (`.../Component/CpuSubsystem.pm`) usually has:

- an `init()` that populates array-ref attributes on `$self`, typically via
  `get_snmp_tables()` / `get_snmp_objects()` (SNMP plugins) or the equivalent DB/RFC
  fetch calls, constructing one object per row/instance of an inner `Item`/`TableItem`
  class defined further down the same file.
- optionally a `check()` — **but usually you don't need to write one.** The inherited
  default `Item::check()` walks every array-ref attribute on `$self` and calls
  `->check()` on each element automatically. You only override `check()` at the
  Component level when you need custom aggregation across items (e.g. "at least N of
  these must be OK").
- the inner `Item`/`TableItem` class does the real per-instance evaluation:
  ```perl
  package CheckNwcHealth::Cisco::IOS::Component::CpuSubsystem::Cpu;
  our @ISA = qw(Monitoring::GLPlugin::SNMP::TableItem);

  sub finish {          # post-process raw SNMP fields into derived attributes
    my ($self) = @_;
    $self->{usage} = $self->{cpmCPUTotal5minRev} // $self->{cpmCPUTotal5min};
    return $self;
  }

  sub check {           # the actual health judgement + output
    my ($self) = @_;
    $self->add_info(sprintf 'cpu %s usage is %.2f%%', $self->{name}, $self->{usage});
    $self->set_thresholds(warning => 80, critical => 90);
    $self->add_message($self->check_thresholds($self->{usage}));
    $self->add_perfdata(label => 'cpu_'.$self->{name}.'_usage', value => $self->{usage}, uom => '%');
  }
  ```
  `TableItem` is for one-of-many rows from an SNMP table; `Item` is for a single
  scalar-ish thing. `finish()` runs once after construction/table-row-mapping and is the
  right place to derive/normalize fields; `check()` is the right place — and the *only*
  place — to call `set_thresholds`/`check_thresholds`/`add_message`/`add_perfdata`.
  Use `protect_value($identity, $key, 'percent'|'positive'|coderef)` when a raw
  SNMP counter/gauge can legitimately come back garbage (negative, wrapped, absent) and
  you want the framework's cached-previous-good-value fallback instead of alerting on a
  transient bad read.

**Looking for a specific GLPlugin method?** `./GLPlugin/.agents/skills/glplugin-reference/`
holds a categorized reference of GLPlugin's method API (status/messages, thresholds,
perfdata, rate/counter state, blacklisting, classification, SNMP fetch helpers, CLI
registration, debugging) with file:line pointers and calling conventions — read it
before guessing a method name or re-implementing something the framework already does.
It lives inside the `GLPlugin` submodule itself, so it stays in sync automatically
whenever that submodule is updated; if `GLPlugin/` is old or not yet initialized (see
"Build system" above), it may not be there yet.

## SNMP: MIBs, OIDs, and the walk/simulation workflow

Applies to plugins built on `Monitoring::GLPlugin::SNMP` (most of them; check whether
`Device.pm` inherits it before assuming — DB/RFC-based plugins, see below, don't).

- `MIBS/` holds the **raw vendor MIB text files** — reference material for figuring out
  what OIDs exist and what they mean. It is not compiled into anything automatically.
- `GLPlugin/lib/Monitoring/GLPlugin/SNMP/MibsAndOids/<MIBNAME>.pm` is the
  **hand-translated, symbolic form** of a MIB the framework already knows about: a flat
  hash of `OID-name => numeric-OID` plus a `mib_ids` entry (the MIB's base OID, used by
  `implements_mib()`). If the MIB you need isn't in that directory yet, you create it by
  reading the raw MIB in `MIBS/` and transcribing the object names/OIDs you need — there
  is no automatic MIB compiler in this toolchain. A new MIB module lives in the
  **GLPlugin submodule**, and its path must be added to `GL_MODULES` in the plugin's own
  `plugins-scripts/Makefile.am` (a relative `../GLPlugin/lib/...` path), exactly like the
  existing entries.
- `implements_mib('SOME-MIB')` and `implements_mib('SOME-MIB', 'someTable')` are how
  classification code (and mode-dispatch code) checks "does this device actually speak
  this MIB" without hardcoding vendor names — prefer this over regex-matching
  `productname` whenever you can, since it tends to generalize better across firmware
  variants of the same model.

### Testing without real hardware

You very likely do not have the real device. Use the plugin's built-in simulation mode
instead of guessing:

```
# 1. Capture real OIDs from an actual device (or ask the user/ticket for one):
check_xxx_health --hostname <ip> --community <community> --mode walk
#    (writes /tmp/snmpwalk_<plugin>_<hostname>; --mode bulkwalk uses snmpbulkwalk instead)

# 2. Replay that capture with no network access at all:
check_xxx_health --snmpwalk <path-to-walk-file> --mode <mode-you-are-implementing>
```
`--snmpwalk` takes priority over `--hostname` and makes every `get_snmp_object`/
`get_snmp_tables` call read from the file instead of the wire — this is the plugin
family's substitute for a unit test suite (there isn't one for vendor/model logic; only
GLPlugin itself has `t/*.t`). **Before declaring a new vendor/model implementation
done, you must run it against a walk file and inspect the actual OK/WARNING/CRITICAL
output and perfdata** — reading the code is not a substitute, since a classify() regex
that looks right can still fail to match the real `productname` string, or an
`implements_mib()` check can be right about the MIB but wrong about which table it
needs. If you don't have a walk file for the device you're adding, ask the user for one,
or ask them to run step 1 against the real device — do not fabricate OIDs.

A walk file is a plain-text snmpwalk-style dump; if a user hands you one directly, or
you already have example OIDs for the target device, you can hand-edit or extend it
rather than re-capturing from scratch.

## Non-SNMP plugins

Not every plugin in this family talks SNMP. `check_sap_health`, for instance, uses SAP
RFC connections instead. The **classify → rebless → mode-dispatch → Component/Item
check()** architecture described above is identical either way — only the data-fetching
calls inside `init()` differ (SAP RFC calls / a DB handle / local `/proc` reads instead
of `get_snmp_object`/`get_snmp_tables`). Before assuming SNMP helpers are available,
check what `Device.pm`'s `@ISA` actually inherits from in the repo you're in.

## Common CLI options — reuse, don't reinvent

These are registered once in GLPlugin (`add_default_args`) or the SNMP layer
(`add_snmp_args`) and are available to every mode in every plugin. A new mode should
compose with these rather than inventing an equivalent flag:

| Flag | Purpose |
|---|---|
| `--warning` / `--critical` | Generic thresholds, consumed by `check_thresholds()` |
| `--warningx KEY=VAL` / `--criticalx KEY=VAL` | Per-item threshold overrides (e.g. one interface, one CPU) |
| `--name` / `--name2` / `--name3` (+ `--regexp`) | Select a specific component to check; `--regexp` makes them patterns |
| `--mitigation` | Downgrade a critical to warning for checks that support it |
| `--lookback SECONDS` | Base rate calculations (interface usage/errors) on a longer window than "since last run" |
| `--blacklist` | Exclude known-bad/missing components instead of alerting on them |
| `--report` (`long`\|short...) / `--multiline` | Control output verbosity/formatting |
| `--morphmessage` / `--morphperfdata` / `--selectedperfdata` | Post-process output text/perfdata without changing check logic |
| `--negate KEY=VAL` | Remap resulting severities (emulates the classic negate plugin) |
| `--statefilesdir` | Where rate/counter state gets cached between runs |
| `--snmpwalk` / `--servertype` | Simulation input / manual override when auto-detection fails |

If you're tempted to add a bespoke `--foo-threshold` flag for a new mode, check first
whether `--warningx`/`--criticalx` with a per-item key already covers it.

## Versioning and changelog

- Version lives in **`configure.ac`**: `AC_INIT([check_xxx_health],[X.Y])` (or
  `X.Y.Z.W` for a hotfix on a released minor). Bump it here; `autoreconf` propagates it
  into the built plugin's `--version` output.
- Add a corresponding entry at the **top** of `ChangeLog`, matching the existing format:
  ```
  * YYYY-MM-DD X.Y
    add <Vendor> <Model>
    <one line per notable change, imperative mood>
  ```
- A new vendor/model addition is a minor version bump (`X.Y` → `X.(Y+1)`), not a patch,
  unless it's fixing an existing vendor's bug.

## Definition of done for "add vendor/model X"

1. `Device.pm` (or the relevant vendor class) reblesses into your new class based on
   `productname` and/or `implements_mib()` — verified against a real or walked device,
   not assumed from a datasheet.
2. Every mode you claim to support is reachable: `add_mode()` exists for genuinely new
   check *kinds*; your model class's `init()` dispatches the mode to a Component class
   that either exists already (reuse it) or that you added.
3. New files are listed in `plugins-scripts/Makefile.am`'s `EXTRA_MODULES` (and
   `GL_MODULES` too, if you added a MIB module inside `GLPlugin/`).
4. `./configure && make clean && make` succeeds and produces
   `plugins-scripts/check_xxx_health` with your class reachable
   (`grep YourClass plugins-scripts/check_xxx_health` is a fast sanity check that the
   file actually got bundled).
5. Run the built plugin against a walk file (real capture, or one you were given) for
   every new mode, and confirm the output text, status, and perfdata make sense —
   not just that it doesn't crash.
6. `configure.ac` version bumped and `ChangeLog` updated.
